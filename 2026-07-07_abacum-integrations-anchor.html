How our integrations work — and why the model is different

Roughly 50 native, first-party connectors cover the high-frequency systems. Finch unifies HRIS, Fivetran covers the long tail, and an Import API plus SFTP/S3 handle anything custom. The point underneath all of it: the connection is the same for every customer, so setup is self-serve — no per-customer engineering.
The one line Self-serve is the biggest difference. Competitors connect data one customer at a time (partners, an army of solution engineers). We made the architectural investment upfront so the flow after "Connect" is autonomous. The typing layer and the custom routes answer the "but we can't customize" objection without reintroducing that headcount.

The strategy — and the trade-off we made on purpose

Strategy · self-serve by design
  • The connection is identical for every customer — so everything after "Connect" is an autonomous, self-served flow.
  • No engineers required to use it, no partner or SI to provision it.
  • We took the long-term view: heavy architectural investment upfront so integration isn't a per-deal cost later.
  • Result: faster time-to-value, lower TCO, fewer dependencies to renew.
Trade-off · and how we cover it
  • One shared connector per system → less bespoke customization out of the box.
  • Typing layer: drop columns you don't need, type and map the rest — efficiency without a custom build.
  • Import API: custom endpoints and coded logic when you genuinely need them (customer tech team required).
  • SFTP / S3: file-based ingestion for enterprise / SAP where a live connection isn't available.
Net: standardized and self-serve by default; customization on demand — without reintroducing the army of solution engineers.
